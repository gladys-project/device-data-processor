# device-data-processor guidance

This is a Gladys service skeleton with the explicitly requested MapStruct message projection. Production Java includes the bootstrap, generated inbound/outbound models, RawTelemetryToDeviceDataMapper and the user-authored DeviceDataProcessorEvent. Its explicitly required public signature is Function<Flux<Message<String>>, Flux<Message<String>>>; do not change it. The user authorized JSON serialization and generated-model validation within that existing function. Do not add further consumer/function implementations, listeners, additional transformations, routing, device management, persistence, watering logic or other core behavior without a later explicit request. Do not add device/watering business rules. Validation must use OpenAPI-generated Jakarta annotations via Validator, without duplicating field constraints in handwritten checks. Do not change DLQ reliability behavior without a separate request.

Use Java 25 without preview, one Maven module, Spring Boot WebFlux/Reactor, Spring Cloud Stream/Function with the Kafka binder, Lombok/SLF4J and the Maven Wrapper. Let the pinned Boot/Cloud BOMs manage compatible dependencies. Keep Lombok annotation processing explicit. No Spring MVC, Reactor Kafka, MQTT client, database or Kubernetes in this skeleton.

Follow TDD and KISS: write a meaningful failing test, run it and confirm its failure, then implement the smallest passing change. Report actual results only. Preserve unrelated work and existing instructions. Update tests and README with relevant changes.

The standalone OpenAPI 3.1.2 contract under src/main/resources/openapi/kafka-raw-telemetry.yml mirrors the MQTT bridge's raw Kafka output; the nested payload/error schemas are embedded so this repository builds independently. Generate models during Maven generate-sources under ignored target/; never edit or commit generated Java. Keep full device envelope, diagnostics and extensible sensor payload intact. deviceId is the Kafka key; soil is resolved downstream using sensorId. A device can have multiple sensors in different soils. Keep the raw input contract intact and do not invent soilId/plant assumptions. The user-authorized outbound KafkaDeviceData projection intentionally omits the sensor payload while preserving all observation correlation and device diagnostics; it must not mutate the input.

application.yml declares processDeviceData-in-0 on gladys.telemetry.raw.v1 and processDeviceData-out-0 on gladys.device.data.v1 (DEVICE_DATA_TOPIC override) with a dedicated gladys.device-data-processor.v1 consumer group. Default/local execution has empty function definition, disabled autodetection and inactive bindings. The deployed profile selects the existing processDeviceData function and enables both bindings. Default/local binding inactivity is independent of the bean being present. Compose selects deployed. Keep Kafka settings under spring.kafka.* and binding settings under spring.cloud.*; no automatic topic creation or partition changes.

./mvnw test runs fast tests without Docker or brokers. ./mvnw clean verify also runs *IT tests through Failsafe and requires Docker; never silently skip. Integration tests start pinned Apache Kafka with explicit readiness checks, provision topics only in tests, exercise the actual production function and verify its string input/output, generated-model validation and device-data Kafka output with bounded waits and exact key/payload assertions. Do not register a replacement test function with the production bean name. The existing DLQ is provisioned only in tests; production provisioning stays external.

Keep the web runtime reactive and expose only Actuator health/info by default. Use StepVerifier for actual reactive publishers. Avoid .block(), .join(), Thread.sleep() and blocking Kafka operations in production event/request paths. Spring Kafka and the regular Kafka binder do not provide end-to-end Reactor backpressure. Keep blocking test orchestration bounded and clearly in tests.

Secrets stay outside Git/logs/images. .env.example is placeholder-only; the JVM does not automatically load env files. Reuse /etc/gladys/gladys.env with docker compose --env-file; forward only this service's settings, never the entire shared file. Root Compose contains only this application and joins an existing external gladys network. Kafka/Mosquitto are managed independently; do not add or restart brokers here. Pin images/actions/plugins and check official compatibility references. Do not commit, push, deploy or modify server configuration unless requested for this repository.

Define the outbound message separately in src/main/resources/openapi/kafka-device-data.yml; reuse DeviceError through the inbound contract reference. Generate KafkaDeviceData through OpenAPI Generator and mapper implementations through MapStruct 1.6.3 with lombok-mapstruct-binding 0.2.0. Use Spring component model, constructor injection and ERROR policies for unmapped source/target fields. Ignore only the intentionally excluded raw payload; deep-copy diagnostic collections/elements. The function maps DTOs internally, serializes the output once to JSON String, and sets KafkaHeaders.KEY to deviceId. Configure the output producer with native StringSerializer encoding and headers['kafka_messageKey'] as its key expression. Code generation adds type-use @NotNull for non-null error-array entries required by the message definitions; never edit generated Java.

GitHub Actions CI/deploy/release workflows follow the MQTT bridge pattern, adapted to device-data-processor. Keep self-hosted runners, immutable action SHAs, Java 25, pinned Compose setup in both build/deploy jobs, Docker-required clean verify and exact verified-artifact reuse. CI validates only this service's Compose file; there is no infra/ stack in this repository. Automatic deployment is allowed only after PR merge into main, plus manual workflow_dispatch branch selection. Serialize all deployments to the same service. Version tags publish JAR releases independently; only publication gets contents:write. Do not trigger deployments/tags/releases merely to test workflows.

The deployment script must set DEVICE_PROCESSOR_IMAGE to a commit-specific image and target only the device-data-processor project/service. Read /etc/gladys/gladys.env directly or through the pinned temporary Docker env-reader fallback; keep its private copy out of logs/artifacts/images and delete it on exit. The local gladys.env is private, ignored, mode 600 and prepared for manual server merging; never stage, commit or push it. Preserve bridge/shared/server variables when adding this service's entries. Run .github/tests/test_deploy.py and actionlint for workflow/script edits, then relevant Maven/Compose/image checks. Do not modify unrelated repositories or broker lifecycle.
